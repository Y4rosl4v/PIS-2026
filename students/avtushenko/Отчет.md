### 2. Use-case описание

👉 **Ссылка на файл:** [use-case.md](use-case.md)

**Основной сценарий:** Прохождение мини-курса и сдача итогового теста

**Первичный актор:** Студент

**Цель:** Пройти видеоурок, сдать итоговый тест, зафиксировать прогресс и получить цифровой бейдж

**Краткое описание основного потока:**
1. Студент открывает каталог и выбирает курс
2. Нажимает "Начать обучение"
3. Система создаёт запись прогресса IN_PROGRESS и открывает видеоплеер
4. Студент просматривает видео до 100%
5. Система разблокирует раздел "Итоговый тест"
6. Студент отвечает на вопросы и нажимает "Завершить тест"
7. Система валидирует ответы, подсчитывает балл и обновляет статус курса
8. При score >= 80% система генерирует бейдж и меняет статус на COMPLETED
9. Студент оставляет комментарий к уроку
10. Система отправляет push/email-уведомление об успешном завершении

**Альтернативные потоки:** Не досмотрел видео (<100%), не сдал тест (попытка <80%), комментарий отклонён модерацией.

**Исключительные ситуации:** Видео CDN недоступен, таймаут при отправке теста, БД недоступна при сохранении прогресса, Notification Service не отвечает.

### 3. Диаграммы последовательности (Sequence Diagrams)

#### 3.1. Happy Path (успешный сценарий)

👉 **PlantUML исходник:** [sequence-happy.puml](diagrams/sequence-happy.puml)

![Диаграмма успешного сценария](diagrams/image_2026-05-19_00-02-09.png)

**Описание потока:**
- Клиент запрашивает старт курса → API Gateway создаёт запись прогресса → CDN отдаёт видеопоток → Клиент отправляет heartbeat'ы → При 100% разблокируется тест → Клиент отправляет ответы → Course Service валидирует, обновляет БД (Tx2), публикует событие CourseCompleted → Event Bus передаёт событие воркеру уведомлений → Студент получает бейдж и push-уведомление.

**Участники:**
- Студент
- API Gateway
- PostgreSQL
- Video CDN
- Course/Test Service
- Event Bus
- Notification Service

#### 3.2. Error Case (сценарий с ошибкой)

👉 **PlantUML исходник:** [sequence-error-payment.puml](diagrams/sequence-error-notification.puml)

![Диаграмма сценария с ошибкой](diagrams/image_2026-05-19_00-02-27.png)

**Описание потока:**
- Студент успешно сдал тест, транзакция в БД закоммичена (прогресс COMPLETED, бейдж выдан). При асинхронной обработке события CourseCompleted Push Service возвращает TimeoutException. Система не откатывает основную транзакцию, помещает задание в таблицу notification_queue, публикует событие NotificationFailed и возвращает клиенту статус 200 с предупреждением. Фоновый worker повторяет отправку через 5 минут.

### 5. Анализ границ ответственности

👉 **Ссылка на файл:** [analysis.md](analysis.md)

#### 5.1. Транзакционные границы

| Операция | Синхронная/Асинхронная | Откат при ошибке | Retry-стратегия | Идемпотентность |
|----------|------------------------|------------------|-----------------|-----------------|
| Валидация доступа к курсу (роль, оплата) | Синхронная | Нет (возврат 403/404) | N/A | Да (чтение без side-effects) |
| Обновление прогресса просмотра видео | Синхронная | Нет (soft-update) | 3 попытки (500ms) | Да (heartbeat с версией) |
| Разблокировка итогового теста | Синхронная | Да (ROLLBACK Tx1) | Нет | Да (проверка video_completed) |
| Сохранение ответов теста | Синхронная | Да (ROLLBACK Tx2) | Нет | Да (idempotency_key) |
| Подсчёт баллов и определение статуса | Синхронная | Да (в Tx2) | Нет | Да (детерминированный алгоритм) |
| Обновление статуса курса + генерация бейджа | Синхронная | Да (в Tx2) | Нет | Да (проверка attempts и лимитов) |
| Публикация событий в Event Bus | Синхронная (outbox) | Да (в основной транзакции) | Нет (часть транзакции) | Да (event_id) |
| Отправка push/email уведомлений | Асинхронная (очередь) | Нет (курс уже пройден) | 5 попыток (exp. backoff) | Да (дедупликация по user_id+event) |
| Фоновая модерация комментария | Асинхронная | Нет | 3 попытки | Да |

#### 5.2. Обработка исключительных ситуаций

**Реализовано стратегий обработки:** 4

**Примеры:**

##### Исключительная ситуация 1: Notification Service недоступен

- **Условие возникновения:** Таймаут соединения или 503 от Push/Email провайдера
- **Обнаружение:** Таймаут 10с при ожидании ответа от сервиса
- **Реакция:** Помещение задания в notification_queue, публикация события NotificationFailed
- **Компенсация:** Основная транзакция НЕ откатывается (данные курса уже в БД)
- **Уведомление пользователя:** "Курс пройден! Уведомление будет доставлено позже."

##### Исключительная ситуация 2: База данных недоступна

- **Условие возникновения:** Connection refused или Query timeout
- **Обнаружение:** DatabaseConnectionException от драйвера
- **Реакция:** Полный ROLLBACK транзакции, возврат HTTP 503
- **Компенсация:** Полный ROLLBACK транзакции, возврат HTTP 503
- **Уведомление пользователя:** "Не удалось сохранить результат. Проверьте интернет или попробуйте позже."
  
##### Исключительная ситуация 3: Видео CDN недоступен

- **Условие возникновения:** Сбой стриминга, HTTP 503, обрыв соединения
- **Обнаружение:** Таймаут плеера > 5с, ошибка Stream Timeout Exception
- **Реакция:** Переключение на резервный CDN/качество 480p. Если не помогло → показ кнопки "Скачать урок"
- **Компенсация:** Прогресс фиксируется по клиентским heartbeat'ам, бизнес-логика не зависит от CDN
- **Уведомление пользователя:** "Видео временно недоступно. Попробуйте обновить страницу."

## Контрольные вопросы

**Подготовка к защите:**

1. Что такое транзакционная граница? Где она проходит в вашем сценарии?
   - Транзакционная граница определяет набор операций, которые выполняются атомарно (все или ничего). В моём сценарии она проходит на уровне Course/Test Service. Граница №1: фиксация 100% просмотра видео + разблокировка теста. Граница №2: сохранение ответов теста + подсчёт баллов + обновление статуса курса + генерация бейджа. Асинхронные уведомления вынесены за границу основной транзакции.

2. Почему операция X выбрана синхронной, а Y - асинхронной?
   - Сохранение результатов теста и статуса курса (X) выбрано синхронным, так как это критичный инвариант домена: студент должен мгновенно увидеть корректный результат, а данные о прогрессе не могут быть частично записаны. Уведомления и модерация комментариев (Y) выбраны асинхронными, потому что они не влияют на целостность учёта прогресса, не блокируют UI и допускают eventual consistency.

3. Как обеспечить идемпотентность при повторных запросах?
   - Клиент генерирует уникальный idempotency_key (например, U-42_C-101_attempt_20241108_100500) и передаёт его в заголовке. Backend сохраняет этот ключ в таблице/кэше вместе с результатом обработки. При повторном запросе с тем же ключом система возвращает закешированный ответ без повторного выполнения бизнес-логики и записи в БД. TTL ключа — 1 час.

4. Что произойдёт, если внешний сервис вернёт ошибку после частичного выполнения операции?
   - Используется паттерн Transactional Outbox. Если Event Bus недоступен во время коммита, событие CourseCompleted записывается в таблицу outbox внутри той же БД-транзакции. Если транзакция успешно закоммичена, фоновый worker гарантирует доставку события позже. Если ошибка произошла до коммита (например, валидация не прошла), происходит полный ROLLBACK, и данные не попадают в БД.

5. Как система обнаружит, что внешний сервис недоступен?
   - Через механизмы health-checks, мониторинг кодов ответов HTTP (5xx/timeout), метрики задержек (p95 latency), размер очереди retry (notification_queue_size) и алерты из системы мониторинга (Prometheus/Grafana). При превышении порога ошибок сервис помечается как degraded.

6. Какие данные нужно логировать для диагностики сбоев?
   - trace_id, user_id, course_id, idempotency_key, timestamp, статусы транзакций (BEGIN, COMMIT, ROLLBACK), коды ошибок внешних сервисов, длительность выполнения операций, IP/DeviceID, уровень логирования (INFO/WARNING/ERROR/CRITICAL).
