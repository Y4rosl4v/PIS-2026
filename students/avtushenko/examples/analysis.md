# Анализ границ ответственности

**Система:** Платформа мини-курсов «Учусь быстро» ▶️  
**Сценарий:** Прохождение мини-курса и сдача итогового теста

---

## 1. Транзакционные границы

### 1.1. Где начинается и заканчивается транзакция?

**Начало транзакции:** Студент нажимает кнопку "Завершить тест" (или система фиксирует 100% просмотра видео для разблокировки).

**Конец транзакции (успешный сценарий):**
- **Основная транзакция БД №1:** Прогресс просмотра обновлён → 100% + Тест разблокирован.
- **Основная транзакция БД №2:** Ответы сохранены + Результат подсчитан + Статус курса обновлён (COMPLETED/IN_PROGRESS) + Бейдж сгенерирован.
- **Побочные эффекты (асинхронные):** Push/Email-уведомления отправлены, комментарии сохранены, события опубликованы в Event Bus.

**Важно:** У нас две отдельные транзакции:
1. **Отслеживание прогресса видео и разблокировка теста** - атомарно для текущего урока.
2. **Сдача теста и фиксация завершения курса** - атомарно. Если тест не сдан, прогресс курса остаётся IN_PROGRESS, но попытка теста сохраняется для анализа.

### 1.2. Какие операции должны быть атомарными?

#### Транзакция №1: Фиксация просмотра и разблокировка теста

**Атомарные операции (в одной БД-транзакции):**
1. Обновление записи прогресса урока (lesson_progress) до 100%
2. Проверка условия разблокировки (video_watched == true)
3. Обновление статуса урока на UNLOCKED для теста
4. Сохранение временной метки завершения

**Обоснование:** Тест не должен стать доступным, если прогресс видео не зафиксирован. Рассинхронизация приведёт к обходу обязательного контента.

**Пример сбоя:**
- Если обновление прогресса прошло, но статус теста не обновился → ROLLBACK. Иначе студент не сможет сдать тест или сдаст его без просмотра материала.

#### Транзакция №2: Сдача теста и завершение курса

**Атомарные операции (в одной БД-транзакции):**
1. Валидация и сохранение ответов теста (test_attempts)
2. Подсчёт баллов и определение статуса (passed/failed)
3. Обновление общего прогресса курса (course_progress)
4. Если score >= 80%: обновление статуса курса на COMPLETED, генерация записи бейджа (badges)

**Обоснование:** Результат теста, статус курса и бейдж должны обновиться одновременно. Частичное сохранение нарушит бизнес-логику (например, курс COMPLETED, но бейджа нет).

### 1.3. Какие операции могут быть асинхронными?

| Операция | Обоснование |
|----------|-------------|
| Отправка push/email уведомлений о завершении | Может быть отложена. Курс уже пройден, уведомление - это "best-effort" действие |
| Публикация доменных событий (CourseCompleted, CommentPosted) | Eventual consistency допустима. События пишутся асинхронно через outbox pattern |
| Фоновая модерация комментария (нейросеть/правила) | Не блокирует публикацию, комментарий помечается как PENDING_REVIEW |
| Обновление аналитики и статистики платформы | Можно пересчитать позже через агрегаторы |
| Генерация динамического сертификата/PDF | Тяжёлая операция, выполняется фоновым worker'ом |

**Принцип:** Если операция НЕ нарушает инварианты доменной модели при отказе - она может быть асинхронной.

|----------|------------------------|------------------|-----------------|-----------------|

| **Обновление кэша популярности курса** | Асинхронная | Нет (eventual consistency) | 3 попытки (1s) | Да |

## 3. Обработка отказов внешних сервисов

### 3.1. Notification Service недоступен

**Проблема:** Сервис push/email-рассылок не отвечает (таймаут, 503).

**Стратегия:**
1. **Таймаут:** 10 секунд
2. **Основная транзакция:** НЕ откатывается (прогресс и тест уже сохранены)
3. **Retry:**
   - Помещаем уведомления в очередь `notification_queue`
   - Фоновый worker пытается отправить повторно
   - Retry schedule: через 1 минуту, затем 5 минут, 15 минут, 1 час, 6 часов
   - После 5 неудачных попыток → помечаем как "failed" и алертим админа
4. **Fallback:** Показать в UI "Уведомление будет доставлено позже"
5. **Уведомление пользователя:** "Курс пройден! Уведомление отправится, когда сервис восстановится."

**Обоснование:** Уведомления вторичны. Студент видит результат на экране, данные сохранены.

### 3.2. База данных недоступна

**Проблема:** PostgreSQL не отвечает (connection refused, timeout)

**Стратегия:**
1. **Таймаут:** 5 секунд для connection, 30 секунд для query
2. **Основная транзакция:** ROLLBACK (заявка и группа НЕ создаются)
3. **Retry:**
   - На уровне приложения: 3 попытки с экспоненциальной задержкой (1s, 2s, 4s)
   - Если все 3 попытки не удались → возвращаем 503 Service Unavailable
4. **Компенсация:** Нет (ничего не было создано)
5. **Offline-режим:**
   - Если нет сети → ответы и прогресс кешируются в IndexedDB/LocalStorage.
   - При восстановлении связи → синхронизируем с сервером
6. **Уведомление пользователя:** "Не удалось сохранить результат. Проверьте интернет или попробуйте позже."

**Обоснование:** БД критична. Без неё потеря прогресса недопустима. Offline-кеш покрывает полевые/нестабильные условия.

### 3.3. Видео CDN недоступен

**Проблема:** Потоковое видео не грузится или обрывается.

**Стратегия:**
1. **Таймаут:** 5 секунд
2. **Основная транзакция:** НЕ откатывается (прогресс фиксируется по клиентским heartbeat'ам)
3. **Fallback:**
   - Автоматическое переключение на резервный CDN или качество 480p
   - Если резерв недоступен → показ кнопки "Скачать урок" или "Пропустить видео" (если разрешено бизнес-правилами)
4. **Уведомление пользователя:** "Видео временно недоступно. Прогресс сохраняется."

**Обоснование:** CDN - инфраструктурный слой. Бизнес-логика (прогресс, тесты) не должна зависеть от него напрямую.

### 3.4. Конкурентное обновление прогресса (синхронизация с нескольких устройств)

**Проблема:** Студент смотрит курс на телефоне и десктопе одновременно.

**Стратегия:**
1. **Блокировка:** Optimistic Locking через поле version или last_updated_at
   ```sql
   UPDATE course_progress 
   SET video_percent = 85, version = version + 1 
   WHERE user_id = 'U-42' AND version = :current_version;
   ```
2. **Основная транзакция:** Если affected_rows == 0 → конфликт версий. Применяем стратегию Last-Write-Wins или мердж максимального прогресса.
3. **Компенсация:** Сервер возвращает актуальный прогресс клиенту для синхронизации UI.
4. **Уведомление пользователя:** "Прогресс синхронизирован с другого устройства."

**Обоснование:** Pessimistic locking убьёт производительность при одновременном просмотре. Optimistic locking + LWW оптимальны для LMS.

## 4. Идемпотентность

### 4.1. Проблема: Повторное нажатие "Завершить тест"

**Сценарий:** Студент дважды кликнул кнопку из-за лага сети.

**Решение:**
1. **Frontend:** pointer-events: none после первого клика.
2. **Backend:** Проверка idempotency_key в заголовке или теле запроса.
   ```json
   {
  "course_id": "C-101",
  "answers": [...],
  "idempotency_key": "U-42_C-101_attempt_20241108_100500"
   }
   ```
3. **Логика:**
   - Проверка таблицы idempotent_submissions.
   - Если ключ есть → вернуть кэшированный {score: 80%, passed: true}.
   - Если нет → обработать, сохранить результат и ключ. TTL ключей: 1 час.

### 4.2. Проблема: Дубликаты уведомлений

**Сценарий:** Очередь обработала сообщение дважды из-за crash worker'а.

**Решение:**
1. Уникальный индекс в notification_queue:
   ```sql
   CREATE UNIQUE INDEX idx_notify_dedup ON notification_queue(user_id, event_type, created_at::date);
   ```
2. При ON CONFLICT → игнорировать вставку.
3. SMS/Push-провайдеры также дедуплицируют по Message-ID.

### 4.3. Проблема: Повторная попытка теста сверх лимита

**Сценарий:** Студент пытается сдать тест в 4-й раз (лимит 3).

**Решение:**
1. Проверка перед транзакцией:
   ```sql
   SELECT COUNT(*) FROM test_attempts WHERE course_id = 'C-101' AND user_id = 'U-42';
   ```
2. Если count >= max_attempts → вернуть 400 Bad Request: LimitExceeded.
3. Уведомление: "Лимит попыток исчерпан. Обратитесь к куратору."

## 6. Метрики и мониторинг

**Ключевые метрики для отслеживания:**

| Метрика | Цель | Алерт при |
|---------|------|-----------|
| `test_submission_latency_p95` | < 2 секунды | > 4 секунд |
| `test_pass_rate` | > 65% | < 50% |
| `video_completion_rate` | > 80% | < 60% |
| `db_connection_pool_active` | < 80% от макс. | > 90% |
| `notification_queue_size` | < 500 | > 2000 |
| `notification_delivery_rate` | > 95% в течение 5 минут | < 90% |
| `cdn_error_rate` | < 0.1% | > 1% |
| `idempotency_cache_hit_rate` | > 95% | < 80% |
| `concurrent_progress_conflicts` | < 10/hour | > 50/hour |
| `offline_sync_pending_count` | 0 | > 100 |

**Логирование:**
- **INFO:** Успешная сдача теста, курс пройден, комментарий опубликован
- **WARNING:** Таймаут Notification Service, помещено в очередь
- **WARNING:** Превышен лимит попыток теста
- **ERROR:** БД недоступна, откатили транзакцию
- **ERROR:** CDN недоступен, fallback активирован
- **CRITICAL:** Очередь уведомлений переполнена (> 5000)
- **CRITICAL:** Массовые сбои валидации тестов (возможна ошибка в контенте)

## 7. Выводы

### Ключевые решения:

1. ✅ **Две транзакции:** Прогресс видео (Tx1) и сдача теста (Tx2) разделены для гибкости и отказоустойчивости
2. ✅ **Атомарность:** Ответы + результат + статус курса + бейдж в одной транзакции
3. ✅ **Асинхронность:** Уведомления, аналитика и модерация комментариев вынесены в очередь
4. ✅ **Идемпотентность:** idempotency_key защищает от дублирующих отправок теста
5. ✅ **Optimistic Locking:** version-поле предотвращает конфликты прогресса с разных устройств
6. ✅ **Отказоустойчивость:** Не откатываем прогресс при сбое уведомлений; Offline-режим кеширует ответы
7. ✅ **Retry:** Exponential backoff для временных сбоев (Push, Email, CDN)
8. ✅ **Мониторинг:** Метрики для каждого критичного компонента + алерты

### Транзакционные инварианты:

- **Инвариант №1:** Тест не разблокируется, пока video_progress < 100% → проверка на уровне приложения + БД constraint
- **Инвариант №2:** Статус COMPLETED присваивается только при score >= passing_threshold → валидация в Tx2
- **Инвариант №3:** Максимальное количество попыток теста строго соблюдается → блокировка на уровне сервиса до начала транзакции
- **Инвариант №4:** Прогресс курса монотонно возрастает или остаётся прежним (не уменьшается при синхронизации) → GREATEST(current, new) логика


### Компромиссы:

- **Eventual consistency для уведомлений:** Студент может получить email с задержкой, но это приемлемо для UX обучения
- **Client-side tracking видео:** Heartbeats могут быть неточными при плохой сети, компенсируется серверной валидацией финального статуса
- **Хранение idempotency_keys 1 час:** Занимает место в Redis/БД, но критично для защиты от двойных отправок
### Риски:

⚠️ **Риск 1:** Очередь уведомлений может переполниться при массовых запусках курсов (например, корпоративное обучение)
- **Митигация:** Лимит очереди + алерт при > 5000 + horizontal scaling consumer'ов

⚠️ **Риск 2:** Студенты могут пытаться обойти прогресс видео через модификацию клиентских запросов
- **Митигация:** Серверная валидация video_watched перед разблокировкой теста + проверка целостности токенов сессии
  
⚠️ **Риск 3:** Конфликт версий при одновременной загрузке с 5+ устройств может привести к потере последних секунд просмотра
- **Митигация:** Реализовать серверный мердж прогресса (брать max(video_percent, local_percent)) вместо строгого LWW
